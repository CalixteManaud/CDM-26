## 3. Sécurité

> Aucune faille **critique exploitable à distance** confirmée. Les points ci-dessous sont des **durcissements**.

### 3.1 À traiter
- **`pages/debug-user.tsx`** — ✅ vérifié : page de debug exposée en prod (derrière auth). N'affiche que les données du user courant, mais expose son `clerkId`/`role` sans raison. **À supprimer** (ou gate `role === 'ADMIN'` + `notFound`).
- **`pages/api/upload/image.ts`** — ✅ vérifié : `new IncomingForm()` **sans `maxFileSize` ni `maxFiles`**, **aucune validation de type MIME** au niveau de la route, et **aucun check de permission** (tout user authentifié peut uploader). - **`pages/api/webhooks/supabase.ts`** — comparaison de secret en clair via header `x-supabase-webhook-secret` (pas de HMAC). À confirmer : utiliser une comparaison **timing-safe** (`crypto.timingSafeEqual`) et idéalement la signature HMAC de Supabase.

- **`retry-failed.ts`** — comparaison `header === Bearer ${secret}` non timing-safe. Durcir avec `crypto.timingSafeEqual`.

### 3.2 Durcissements généraux
- **Validation d'URL manquante** sur `matches/[id]/update-stream.ts` et `webhooks/index.ts` (URLs stockées sans `z.string().url()` → risque SSRF théorique sur les webhooks sortants).
- **Headers de sécurité absents** : pas de CSP / HSTS (à ajouter dans `next.config` headers).
- **Pas d'audit log** sur les routes `pages/api/admin/**`.
- **Webhook Clerk** (`webhooks/clerk.ts`) : la réconciliation dev/prod **supprime une row user** sans vérifier ses relations (data-loss possible si la même DB est partagée dev/prod). À confirmer / sécuriser.

## 4. Logique métier — paris (priorité produit)

> Code lu : `lib/utils/betting.ts` (✅ vérifié). Les findings combinés/quotas proviennent de l'analyse auto — **à confirmer**.

### 4.1 Settlement (`lib/utils/betting.ts:184+`) — ✅ vérifié
- **Pas de guard `settledAt` explicite** : la fonction écrit `settledAt = now` puis ne traite que les bets `PENDING`. C'est ce qui **évite le double-crédit** (un 2ᵉ appel ne trouve plus de PENDING). **Conséquence à connaître** : un **re-settlement n'est pas possible** — si un résultat est soumis puis corrigé, les paris déjà settlés ne sont **pas** recalculés/remboursés. 
  - *Action recommandée* : ajouter en tête `if (pool.settledAt) throw 'ALREADY_SETTLED'` pour rendre l'invariant explicite et bloquer les soumissions multiples côté admin.
- **Pool gagnante vide** (`betting.ts:276-279`) : si `winningPool === 0`, fallback = rembourser la mise (`bet.pointsWagered`). Mathématiquement le `distributablePool` (amputé du house cut) peut être < total remboursé → légère incohérence comptable. En pratique winningPool=0 est quasi-impossible (un gagnant a forcément parié sur l'issue gagnante). Faible.
- **Arrondis / perte de centimes** (`betting.ts:268,278`) : chaque payout est `Math.floor(...)`. Le reliquat (somme des floors < distributablePool) n'est redistribué à personne → micro-perte par match, cumulée sur le volume.
  - *Action* : attribuer le reste au dernier gagnant (boucle avec `remaining`).

### 4.2 Combinés / marchés (`actions/markets.ts`) — ⚠️ à confirmer
- **Jambe VOID dans un combiné** : `evaluateBetSlip` ne semble pas gérer `BetStatus.VOID` (seuls WON/LOST/CREDIT_FAILED testés). Si un marché d'une jambe est annulé, le slip pourrait passer **WON** au lieu d'être recalculé/remboursé. **À vérifier en priorité.**
- **`CREDIT_FAILED` d'une jambe** compté comme « settled » → slip potentiellement crédité alors qu'une jambe n'a pas reçu son crédit.
- **Reliquat de mise sur combiné** : `perLegStake = floor(totalStake / nbLegs)` ; si `totalStake` non divisible (ex. 15/10), des points débités ne sont pas utilisés → soit rejeter, soit informer du montant ajusté.

### 4.3 Fenêtres & quotas
- **Race « check → débit → placeBet »** : la fenêtre `isBettingOpen` et le quota sont vérifiés avant le débit Wizebot, mais le temps peut basculer (fin de match, minuit, fin de fenêtre live 25 min) entre le débit et la création du pari → **débit sans pari** (remboursement manuel). Cf. aussi le `try/catch` de `bets/place.ts` qui log mais ne compense pas automatiquement.
  - *Action* : file/table « refund pending » + cron, ou ordre transactionnel resserré.
- **Quota — reset minuit Paris / DST** : `quotaDayStart` (`lib/utils/quota.ts`) calcule l'offset à la main via `Intl` → fragile au changement d'heure. Envisager `date-fns-tz`/Luxon. À confirmer.
- **Idempotence débit** : pas d'`idempotencyKey` côté Wizebot ; deux POST simultanés (rate-limit en mémoire, par instance) pourraient double-débiter. À confirmer en prod multi-instance.

### 4.4 Bracket / standings
- **Tie-break non déterministe** (`lib/utils/standings.ts`) : à égalité parfaite (points = diff = buts marqués), l'ordre dépend de Postgres → bracket potentiellement différent à chaque recalcul. Ajouter un tie-break stable final (ex. `teamId`).
- **Génération bracket avant fin des poules** (`bracket-generator.ts`) : pas de garde « tous les matchs de groupe FINISHED » → bracket calculé sur des standings partiels. À confirmer / ajouter une vérif `canGenerateBracket`.

## 5. Backend / API — robustesse

### Points forts (✅ vérifiés sur échantillon)
- Toutes les routes vérifient la méthode (405), l'auth Clerk, et les permissions par domaine.
- Transactions Prisma présentes sur les opérations multi-écritures (création tournoi+groupes, submit-result, placeBet).
- Rate-limit (10/min) + quotas jour/match avant débit.

### À améliorer
- **Validation zod incomplète** : `matches/[id]/update-stream.ts`, `webhooks/index.ts`, `admin/markets/settle.ts`, `profile/update.ts` valident à la main ou pas du tout. Créer les schémas zod manquants.
- **Conventions de retour incohérentes** : mélange `{ success, data }`, `{ id }`, `{ webhooks }`. Standardiser sur `{ success, data?, error?, code? }`.
- **Index Prisma** : envisager `@@index([tournamentId, isActive])` sur `Webhook` et un index `type` sur `MatchEvent` si les volumes grossissent.
- **Events webhook hardcodés** (`webhooks/index.ts`) : liste magique à remplacer par l'enum Prisma `WebhookEventType`.
- **CRUD partiel** : la couche API privilégie les writes ; les reads passent par `actions/` (cohérent avec l'archi). Pas un bug, mais à documenter.

- **`CRON_SECRET`** : confirmer qu'il est défini en prod (sinon les GET cron sont rejetés, c'est voulu) et configuré côté Vercel Cron.

### 7.2 Rate-limit & idempotence distribués (multi-instance Vercel)
- **Brancher Upstash KV** pour `lib/rate-limit.ts` (sinon le rate-limit est par-instance → contournable en prod multi-lambda). Variables à fournir : cf. instructions en tête de `lib/rate-limit.ts`.

C'est une **décision d'archi** (à valider avec toi) car ça ajoute une dépendance.

### 7.3 Compensation automatique des débits Wizebot orphelins — ✅ IMPLÉMENTÉ (reste : déployer la migration)
- **Fait en code** : table `PendingRefund` (schéma + migration `20260616120000_add_pending_refund`), `recordPendingRefund()` appelé dans les 3 points de placement (`bets/place`, `markets/place`, `markets/slip`) quand le débit a réussi mais le pari a échoué, et `processPendingRefunds()` rejoué par le cron `/api/admin/bets/retry-failed` (toutes les 5 min). Messages utilisateur mis à jour (« remboursé automatiquement sous quelques minutes »).
- **⚠️ Action manuelle restante** : appliquer la migration sur la base (elle crée la table). Voir §7.8.

### 7.4 Garde « poules terminées » avant génération du bracket — ✅ IMPLÉMENTÉ (blocage dur)
- **Fait en code** : `generateKnockoutBracket` (`lib/utils/bracket-generator.ts`) re-vérifie maintenant directement en base qu'aucun match de poule n'est non-`FINISHED`, **indépendamment** du flag `groupStageComplete`. Si un match de poule traîne → erreur explicite, génération refusée (blocage dur). S'ajoute à la garde existante de `complete-group-stage`.

### 7.5 Webhook Supabase — suppression d'utilisateur
- Le `DELETE` propage un `client.users.deleteUser()` côté Clerk sans vérifier les relations (paris, équipes). À décider : soft-delete, ou blocage si l'utilisateur a des paris/une équipe. **Risque data-loss** si dev et prod partagent la même base.

### 7.6 Quota — fuseau horaire & changement d'heure (DST)
- `lib/utils/quota.ts` calcule le minuit Paris à la main via `Intl`. Robuste 364 jours/an, fragile aux 2 bascules DST. Si tu veux le fiabiliser à 100 %, ajouter `date-fns-tz` (ou Luxon) — **nouvelle dépendance**, à valider.

### 7.7 CSP (Content-Security-Policy)
- J'ai ajouté HSTS + headers de base, mais **pas de CSP** (Clerk/Vercel/Twitch injectent des scripts → une CSP trop stricte casserait l'app). À faire en mode `Content-Security-Policy-Report-Only` d'abord, observer les violations, puis durcir.

### 7.8 Migration Prisma `PendingRefund` — à déployer
- La migration `prisma/migrations/20260616120000_add_pending_refund/migration.sql` a été **écrite à la main** (table + enum `RefundStatus` + index + FK). Le client Prisma a déjà été régénéré (`prisma generate`).
- **À lancer par toi quand tu es prêt** (touche la base de prod) :
  ```bash
  npx prisma migrate deploy
  ```
  (Utilise `DIRECT_URL`. Pas de `prisma migrate dev` sur le pooler Supabase — cf. CLAUDE.md.)
- Tant que la migration n'est pas appliquée : le code compile, mais tout appel à `prisma.pendingRefund` échouera à l'exécution (table absente). À déployer **avant** de remettre le code en prod, ou en même temps.
